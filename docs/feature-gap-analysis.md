## 1. 結論

1. **功能完成度約兩成。** 原版約 150 個命令（不含字級、Tab 欄數等數值清單），本專案實際可用約 30 個；其餘不是沒有選單項目，就是以灰階停用的佔位項目呈現。
2. **缺的不只是 UI。** 復原/重做、多文件分頁、系統剪貼簿、設定檔保存、自動換行這些編輯器的基本能力都還沒有，其中復原/重做會影響 `src/core/` 的資料結構設計。
3. **建議改用 egui。** 決定性的需求是「使用者可選字型」：原版可以任選字型，連比例字型都支援（`Fixed Width Mode` 可關閉，逐字量測字寬）。這需要逐字字寬量測，Slint 沒有公開這種 API，egui 則是原生能力（見第 3 節）。由於大部分功能都還沒做，現在換框架的相對成本最低。

## 3. 框架評估：Slint 與 egui

### 3.1 決定性需求：使用者可選字型

使用者可以任選字型時，程式無法事先知道每個字的寬度，所以必須在執行期量測：

- 游標、選取範圍、列塊矩形、Hex 三欄對齊，都需要知道每個字畫在哪裡。
- 比例字型（關閉等寬模式）時，每個字寬都不同。
- 等寬的拉丁字型（例如 Menlo）搭配 CJK 後備字型時，中文寬度不會剛好是兩個半形字。
- 自動換行需要知道一行在哪裡超出視窗寬度。

| 能力 | Slint 1.18 | egui 0.35 |
|---|---|---|
| 逐字字寬量測 | **沒有公開 API**，`Text` 只提供 `font-metrics`（上緣與下緣高度） | `Galley` 提供每個字的矩形，`pos_to_cursor` / `cursor_to_pos` 為原生能力 |
| 字型後備鏈 | 由 Slint 內部的 parley/fontique 決定，應用程式無法得知某個字實際用了哪個字型 | `FontDefinitions` 由應用程式自行註冊與排序，量測與繪製使用同一條鏈 |
| 在指定座標畫單一字元 | 只能為每個字建立一個 `Text` 元件，可視範圍內約數千個 | `Painter` 直接繪製，即時模式沒有元件數量的成本 |
| 輸入法 | 可用（本分支以 `TextInput` 代理實作） | 原生事件 `Event::Ime` |

在 Slint 上要支援可選字型，只能自己讀字型檔量測字寬（fontique + skrifa），再為每個字放一個 `Text` 元件。但 Slint 的字型後備可能挑到不同的字型，量測結果和實際畫出來的仍可能不一致。這是繞路，不是解法。

### 3.2 其他面向

| 面向 | Slint | egui | 評估 |
|---|---|---|---|
| 自繪編輯區（游標、選取、括號配對、拼字底線、第 80 欄提示等疊加圖層） | 每一層都是 `for` 迴圈加上由 Rust 推送的資料模型，每次按鍵都要重建 | 每一幀直接繪製 | egui 明顯較簡單 |
| 狀態同步 | 曾發生 Rust 寫入但 UI 沒讀取、兩邊各存一份狀態而不一致（problem.md 中約十項） | 即時模式不會有兩份狀態 | egui 較不易出錯 |
| 對話框、表單（選項、排序、尋找取代等） | 宣告式，較整齊 | 程式碼式，也足夠 | 差不多 |
| macOS 原生選單列 | 1.18 的 `MenuBar` 可以對應 NSMenu | 沒有，需另外整合 `muda` | Slint 較好，但本專案目前也沒用到 |
| 列印 | 沒有 | 沒有 | 都需另行處理（例如輸出 PDF 再交給系統列印） |
| 經典 Win98 外觀 | 已完成 | 需重畫 | Slint 已有的成果會作廢 |

### 3.3 換框架的成本

- **作廢**：`ui/*.slint` 約 1830 行、`src/main.rs` 約 1700 行（大多是 Slint 事件接線）。
- **保留**：`src/core/` 約 4800 行（Piece Table、編碼、搜尋、Hex、語法突顯、列塊選取）完全沿用。
- **相對成本**：第 2 節列出的功能約八成還沒做，而且多數是 UI 密集的功能（對話框、分頁、檢視選項、疊加圖層）。若繼續用 Slint，這些功能都要寫成 Slint 版本，之後再換框架的成本只會更高。

### 3.4 egui 需要先驗證的風險

以下幾點應在原型階段先確認，不要直接全面改寫：

1. **CJK 字型載入**：egui 必須拿到字型檔的位元組。Sarasa 一套字型檔有數十 MB，要確認載入時間與記憶體，以及 `.ttc` 字型集合的支援。
2. **字型渲染品質**：egui 自己光柵化字型，小字級 CJK 在 Windows 低 DPI 螢幕上的清晰度需要實測。
3. **輸入法**：在 macOS 注音／倉頡、Windows 新注音、Linux fcitx5 上實測組字顯示與候選窗位置。
4. **大檔捲動效能**：只繪製可視行，確認每幀的排版成本。

## 4. 建議路線

1. **egui 原型**（建議 2–3 天）：自繪編輯區，從系統字型清單中選擇字型、等寬與比例兩種模式的游標和選取、輸入法、CJK 後備。依 3.4 的四項風險驗證。
2. **原型通過後**：建立 egui 主視窗骨架與經典外觀元件，接上現有的 `src/core/`，把文字、列塊、Hex 三種模式與現有功能移植過去。
3. **補齊核心缺口**（與框架無關，可與第 1、2 步平行進行）：
   - 復原/重做（建議在 Piece Table 層實作）
   - 多文件分頁
   - 系統剪貼簿（`arboard`）
   - 設定檔保存（最近檔案、字型、選項）
   - problem.md 的 P1 資料正確性問題
4. **依原版命令表逐項補齊功能**：依使用頻率排序，先做編輯與檢視，再做工具與巨集。
